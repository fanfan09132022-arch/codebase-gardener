## 为什么要量：从第一性原理出发

一次上线造成的损失，大致由三件事相乘决定：

```
损失 ≈ 出错的概率 × 影响多少用户 × 多久发现并恢复
```

人工审代码只压低第一项，而且对不懂代码的使用者来说几乎压不下来。免审上线要成立，三项都要压，并且都要能量出来：

| 项 | 怎么压 | 怎么量 |
|---|---|---|
| 出错的概率 | 结构、自动检查、自动验证 | 埋雷拦下率；变更失败率 |
| 影响多少用户 | 按风险分级、金丝雀、功能开关、一次只上线一小步 | 错误预算用了多少 |
| 多久发现并恢复 | 上线后健康检查、自动退回 | 恢复时间 |

放权与否，看实测出来的数字，不看 AI 的自评。

## 埋雷测试

在副本里故意放进已知的错误，看关卡拦下几个。用 `scripts/run_mines.py`，见脚本开头的说明。

**雷从哪来。** 同一个 AI 既设计雷又写检查，会有同样的盲区：它想不到的错误，既不会埋，也不会查。所以一个区域的核心雷至少来自两种来源（配置 `min_mine_sources`）：

| 来源 | 怎么做 | 好处 |
|---|---|---|
| `history` 历史 bug | `run_mines.py harvest --commit <修 bug 的提交>`，把修复反过来，测试文件不动 | 真实发生过的错误，不靠想象 |
| `user` 使用者 | 使用者用大白话说「最怕它坏成什么样」，AI 做成补丁 | 来自懂业务的人 |
| `mutation` 变异工具 | Stryker（JS/TS）、mutmut（Python）、PIT（Java）自动生成 | 机械生成，没有 AI 的偏好 |
| `ai` AI 设计 | 用一个**没参与写检查**的新会话设计，最好换一个模型 | 覆盖面广，但盲区最大 |

**规则：**
- 每个核心功能 1 到 3 个雷，起步默认值。功能越碰钱、越复杂，雷越多。
- 核心雷必须全部拦下，区域前提 3 才算 ✅。`release_gate.py` 会检查最近一次结果。
- 补丁放不进去的雷是「失效」，不算拦下。修好补丁，或经使用者批准退役。
- 退役任何核心雷（包括使用者要求删掉没拦下的雷），都要在 `docs/埋雷记录.md` 写明原因。这个功能没有雷覆盖之前，所在区域前提 3 不算达标。
- 每修一个线上 bug，就用 `harvest` 从修复提交生成一个新雷。这是雷库长大的主要来源。
- 雷库的盲区在于它只能证明**想到的**错误被拦下。没想到的错误只能靠事后追账发现。

**先确认关卡测的是这份代码。** 一个区域的雷几乎全部漏过时，先别急着下「测试不够」的结论，`run_mines.py` 会提示先查两件事：
- 关卡跑的测试覆盖不覆盖这个区域。常见情况：发版只跑一小组冒烟测试，而最近的改动都在别处。
- 测试导入的是不是副本里的代码。Python 项目用 editable 安装或 `.pth` 文件时，在副本里跑测试，导入的可能还是开发目录的代码，雷放进副本也测不到。修法是在关卡命令里设好 `PYTHONPATH` 指向副本，并在关卡里打印一次被导入模块的文件路径作证据。Node 项目查 `npm link`。

**变异测试**：项目有自动测试时，每月跑一次，看变异分数的趋势。分数下降就查原因。参照 Google 论文 [State of Mutation Testing at Google](https://research.google/pubs/state-of-mutation-testing-at-google/)。装工具要使用者批准。

**考 AI 体检本身**：用一个会话在副本里埋雷，把答案单独记下；另一个没看过答案的会话做体检；最后对答案。

## 事后追账

只要发生下面任何一种情况，就记一笔：改动被自动退回；上线后由使用者、用户或监控发现了问题；不得不手动修正已上线的内容。

- 自动退回由 `gardener-release.yml` 自动记进上线账本。
- 上线后才发现的问题，在 Actions 页面运行 `gardener-ledger`，选 `record-incident` 登记。
- 两种情况都要在 `docs/漏网记录.md` 写一行大白话：坏了什么、谁发现的、本该拦住它的关卡、为什么没拦住、补了什么。
- 出事的区域**自动暂停**自动上线，这是 `release_gate.py` 按账本判断的，不靠 AI 记得。
- 恢复：补好关卡，用 `harvest` 把这次的 bug 做成雷，重跑埋雷全部拦下，再由使用者本人运行 `gardener-ledger` 选 `resume`。别人点会失败。
- 同一类问题漏网两次，说明整类关卡缺失，回到阶段 3 重新设计。
- 记账是为了补关卡，不追究是谁的错。参照 Google SRE 的 [Postmortem Culture](https://sre.google/sre-book/postmortem-culture/)。

## 放权的依据：实测指标

`release_gate.py check` 对每次上线判断一次，下面任何一条不满足就停下等使用者：

1. **五项前提都有证据**，证据文件存在，并且 90 天内更新过。
2. **最近一次埋雷**在 35 天内，这个区域的核心雷全部拦下，来源至少两种。
3. **没有未解除的暂停。**
4. **变更失败率的上界**不超过 15%。变更失败率是出事的上线次数除以总上线次数，是 [DORA 交付指标](https://dora.dev/guides/dora-metrics-four-keys/)之一。
5. **恢复时间的中位数**不超过 60 分钟。对应 DORA 的失败恢复时间。
6. **错误预算没用完。**

**已有发版记录的项目**，用 `release_gate.py import-history` 把记录导成账本，直接得到实测失败率，不用从 0 次开始攒。导入只认得「退回」，「发出去以后又发一版来修」要按提交信息另估上限，两个数一起报。

**为什么用上界，不用平均值。** 小项目一个月可能只上线十几次。10 次里 0 次出事，不代表失败率是 0，可能只是运气。统计学的[「三法则」](https://en.wikipedia.org/wiki/Rule_of_three_(statistics))说：n 次全部成功时，失败率 95% 置信上界约为 3/n。脚本用的是 [Wilson 区间](https://en.wikipedia.org/wiki/Binomial_proportion_confidence_interval#Wilson_score_interval)，它在样本少时也可靠。结果是：一个新区域大约要连续 22 次成功上线，上界才会低于 15%。这些上线由使用者看证据摘要批准，同时攒记录。这就是「信任靠记录挣来」，取代了旧版的「漏网次数逐月下降」：那种说法在样本小时没有统计意义。

**错误预算。** 每个区域定一个 SLO，即「正常工作的时间占比」目标，例如 99.5%。30 天里允许坏掉的分钟数就是 `(1 − 0.995) × 30 × 24 × 60 = 216` 分钟。每次出事从上线到恢复的分钟数都从预算里扣。预算用完，这个区域停止自动上线，直到窗口滚过去。参照 Google SRE Workbook 的 [Error Budget Policy](https://sre.google/workbook/error-budget-policy/)。

SLO 由使用者定。AI 给建议时说清楚代价：99.9% 一个月只允许坏 43 分钟，意味着更少的自动上线。

## 阈值：哪些是自定的

所有阈值都在 `.gardener/config.json` 的 `thresholds` 里，改它是红色改动。下面是来源，汇报时照实说：

| 阈值 | 默认值 | 来源 |
|---|---|---|
| 变更失败率上界 | 15% | **本 skill 自定的起步值**，没有行业统一标准 |
| 置信度 | 95% | 统计学惯例 |
| 恢复中位时间 | 60 分钟 | **本 skill 自定**，按项目能承受的停机时间调 |
| 埋雷最长间隔 | 35 天 | **本 skill 自定**，对应每月一次 |
| 核心雷来源数 | 2 种 | **本 skill 自定** |
| 证据最长有效期 | 90 天 | **本 skill 自定** |
| 每个核心功能的雷数 | 1 到 3 个 | **本 skill 自定** |
| 同类漏网几次回阶段 3 | 2 次 | **本 skill 自定**，和「同一个错第二次就加检查」一致 |

自定的数字只是起点。跑满三个月后，用实测数据和使用者一起重新定一次。

## 每月复盘

每月 1 号流水线自动重跑埋雷。之后 AI 做一次复盘，写进 `docs/上线就绪.md`：

1. 跑 `release_gate.py report`，把表贴进去。
2. 列出本月埋雷结果，漏过和失效的雷怎么处理的。
3. 列出本月漏网，每条补了什么关卡。
4. 跑 `ledger.sh audit`，确认账本只有流水线写过。
5. 给使用者一句话结论：哪些区域可以考虑扩大放权，哪些要收紧。扩大放权由使用者决定。
