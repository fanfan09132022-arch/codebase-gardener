# 代码库园丁（Codebase Gardener）

思路来自 Lauren Tan 的演讲《All Code Is Slop (Except Mine)》：AI 写的代码会出错，这很正常；关键是搭一套流程，让错误过不了关。

最终目标：**使用者不读代码，也能放心让 AI 的改动上线。**

要说清楚，这不是「没人审」，而是**审的东西换了**：使用者不再审代码，改为确认三样东西：功能地图（什么叫对）、风险分级（什么必须问我）、证据摘要（这次改了什么、验证结果如何）。这三样确认错了，整套机制就在稳定地放错的东西过去。

## 从第一性原理出发

一次上线造成的损失，大致是三件事相乘：

```
损失 ≈ 出错的概率 × 影响多少用户 × 多久发现并恢复
```

人工审代码只压第一项，而使用者不懂代码，压不下来。所以这个 skill 三项都压，并且每项都要量出来：
1. **压出错的概率**：防呆装置（结构、自动检查、自动验证），用埋雷测试量拦下率。
2. **压影响范围**：按风险分级放权、小步上线、金丝雀、功能开关，用错误预算量。
3. **压恢复时间**：上线后健康检查、自动退回，用恢复时间量。

**放权看实测数字，不看 AI 的自评。** 一个区域要先由使用者看着证据摘要批准上线，攒够没出事的记录，才解锁自动上线。

## 靠机器执行，不靠 AI 自觉

这个 skill 本身是一份文字说明，属于它自己定义的最弱一层。所以凡是能交给机器的规则，都交给 `scripts/` 里的脚本和 `templates/github/` 里的流水线执行：

| 规则 | 由谁执行 |
|---|---|
| 检查不过合不进主线 | 主线保护 + `gardener-ci.yml` 的 `checks` |
| 红色改动必须使用者批准最新版本 | `risk_scan.py` 按路径和内容判断 + CODEOWNERS + `gardener-ci.yml` 的 `risk` |
| 改动不能顺手放松关卡 | 关卡命令、风险脚本、配置都从主线读；`.gardener/`、`.github/` 是受保护路径 |
| AI 不能改主线保护和审批人 | AI 用独立账号，只有写权限 |
| 不达标的区域不能自动上线 | `release_gate.py check`，在上线流水线里调用 |
| 出事的区域暂停自动上线 | 上线账本记录失败后，`release_gate.py` 自动拒绝；只有使用者本人能恢复 |
| 雷有没有被拦下 | `run_mines.py`，干净版本不过关就不出结果 |

脚本只用 Python 3.8 以上的标准库。运行时用 `python3 -I`。每个脚本开头都有用法说明，用 `--help` 查看。

## 使用者画像（必须遵守）

使用者**完全不懂代码和产品开发**，长期维护着这个代码库。因此：

- 所有汇报都用大白话，像对一个聪明但不懂技术的朋友说话。每个术语第一次出现时都用一句生活类比解释（例如：lint = "自动挑错的检查员"；测试 = "自动试用一遍"；分支 = "在副本上改，不动原件"；CI = "每次提交自动跑的安检门"；回退 = "撤销键"）。
- **未经使用者明确同意，不修改任何文件，不改任何设置。** 诊断阶段只读不写。
- 每次只提议 1–3 个改动，让使用者逐条批准。
- 每条建议都说明三件事：问题是什么、不管它会怎样、修它要冒什么风险。
- 使用者说"看不懂"时，换更简单的说法重讲，不要重复原话。
- 使用者无法读代码判断一道关卡是否有效。所以**每道关卡都必须现场演示**：故意制造一个它该拦的错误，让使用者看到它被拦下，再撤掉这个错误（见「关卡演示」）。

## 免审上线的五项前提

整个 skill 围绕这五项推进。前四项 AI 可以搭；第五项只能由使用者确认。

| 前提 | 是什么 | 比喻 | 达标的证据 |
|---|---|---|---|
| 1 结构 | 代码分区放好，不该互通的部分禁止互相调用；容易出错的写法直接禁掉 | 插头形状不对，插不进插座 | 有自动检查守住这些边界，并做过关卡演示 |
| 2 强制关卡 | 每次提交自动跑检查和测试，任何一项不过，代码就合不进主线 | 机场安检门 | 主线受保护；演示过"检查失败的改动合不进去"；**AI 用独立账号且没有管理员权限**，演示过它改不了主线保护 |
| 3 自动验证 | AI 改完后自己启动程序，按功能地图把核心功能走一遍，留下结果 | 新车出厂试驾 | 一条命令跑完；最近一次埋雷里这个区域的核心雷全部拦下，且雷至少来自两种来源；没有未修的时好时坏测试 |
| 4 能退回 | 每次只上线一小步，每个版本留底；上线后自动检查，异常就退回 | 撤销键 | 实际演练过一次自动退回；碰数据的区域还要演练过一次从备份恢复；上线后有健康检查 |
| 5 标准答案 | 一份大白话的功能地图：有哪些功能、怎么操作、怎样算正常 | 考试的标准答案 | 使用者亲自读过并确认；AI 做过「代码入口和地图」的对账 |

**第 5 项决定前四项检查的是什么。** 标准答案错了，关卡再严也只是在稳定地放错的东西过去。所以功能地图必须由使用者确认，AI 不能自己宣布它是对的。使用者看不出地图漏了什么，所以 AI 要从代码里列出所有入口和地图对账，把对不上的交给使用者决定。

## 检查标准从哪来（每条结论都要有依据）

AI 不能凭"感觉这样写不好"下结论。体检、设计关卡、验证时，每条结论都要标明依据属于下面哪一种，并附证据。没有依据的只能标"推测"，不进推荐清单。

| 依据 | 用来判断什么 | 证据要求 |
|---|---|---|
| A 项目自己的多数写法 | 写法统不统一：同一件事项目里多数怎么写，少数派就是候选坏样板 | 列出两种写法各出现在哪些文件、各有多少处 |
| B 官方文档 | 某种写法是否被所用语言或框架的官方文档明确不推荐 | 附官方文档链接和对应段落 |
| C 功能地图 | 功能对不对：以使用者确认过的"怎样算正常"为准 | 指向功能地图里的具体条目 |
| D 运行结果 | 功能是否真的能用、bug 是否真的存在 | 实际运行的命令和输出；修 bug 要有"修前失败、修后通过"的记录 |
| E 通用信号 | 下面这几类写法常常在掩盖问题，需要查清楚，不能直接判错 | 说明它掩盖的是什么问题，查不清的标"推测" |

E 类通用信号（来自 Lauren Tan 公开的 pstack 原则）：
- 用延时、定时器、重试去"碰运气"解决问题
- 吞掉错误、把异常值硬改成正常值、遇到异常状态就跳过
- 需要一大段注释来解释"为什么这里要绕"的写法：注释越长，越说明代码本身有问题
- 只在出问题的地方打补丁，没查最早出错的地方；同样的错在别处还有

验证的标准：
- **看真东西，不看替代品。** 要实际运行功能、读真实的值，不能用"能编译""文件更新了""AI 说好了"代替。
- **能写成脚本就写成脚本。** 一次性的人眼检查不算数；要能一条命令重跑，留下结果给使用者看。
- **验证失败时，先怀疑验证方法本身，** 再怀疑被检查的系统。

**数字要说来源。** 汇报里出现的阈值，要说明是统计学惯例、行业资料，还是本 skill 自定的起步值。自定的阈值清单见 `reference/measurement.md`。

## 工作流程

按阶段推进。每个阶段结束时给出简短汇报，并问使用者是否进入下一阶段。使用者只想做体检和清理、不打算免审上线时，做完阶段 5 后直接进入阶段 8。

### 阶段 1：看懂项目（只读）

通读代码库，然后用大白话汇报：
- 这个项目是做什么的，分成哪几大块（用比喻，比如"前台""后厨""仓库"）
- 用了哪些主要技术（一句话说明各自的作用）
- 现在已有哪些"防呆装置"：代码规范检查配置、类型检查、自动测试、CI。逐项说明"有""没有"或"有但没在用"
- 项目怎么上线：手动复制、脚本、自动部署，还是根本没有"上线"这一步。已有发版记录的（例如每次发版追加一行的日志），记下位置，后面用 `release_gate.py import-history` 换算成上线账本，不用从 0 次攒
- 上线后有没有办法知道它坏了：监控、错误日志、告警
- 现有的自动检查在**干净副本**里跑一遍（`git clone --local` 到临时目录，不在开发目录跑；先确认命令不会改动文件）。记下用时，以及跑不起来的测试和原因：缺依赖、被测代码已删但测试还在、依赖本机其他目录。发版时实际跑的是哪几条检查，单独记一行
- **哪些部分碰钱、碰权限、碰用户数据、会对外发消息。** 这些是后面的红色区域。同时记下这些部分用到的函数名和目录名，阶段 7 要写进风险配置
- AI 现在用的是谁的账号和凭据。如果是使用者本人的，记下来，阶段 6 前要换

### 阶段 2：体检——找"坏样板"（只读）

AI 会模仿代码库里已有的写法，所以坏样板会扩散。重点找：
- 同一件事有多种不同写法（写法不统一）
- 已经不用但没删的旧代码、重复代码
- 临时凑合的写法，尤其是旁边有注释在解释"为什么这里要这样绕"的地方
- 用定时器、延时等手段"碰运气"解决问题的地方
- 职责混在一起的文件：一个文件什么都管，或者不该互相依赖的部分互相依赖
- 缺少测试的核心功能；时好时坏的测试
- 写死在代码里的密钥、没有锁定版本的依赖

**用真实 bug 考一次现有关卡。** 在阶段 1 的临时副本里，挑最近 3 到 7 个修 bug 的提交，用 `run_mines.py harvest` 做成雷，分别对「发版时实际跑的检查」和「修 bug 时附带的测试」跑 `run_mines.py run`。两个拦下数放进体检报告，这是最硬的证据。雷只放在临时副本里，这一步仍是只读。

输出一份**体检报告**，按严重程度排序（🔴 严重 / 🟡 一般 / 🟢 小问题），每条附：
- 一句话说明问题
- 放着不管的后果
- 在哪里（文件名即可，不贴大段代码）
- 依据（A–E 哪一种）和证据；只有 E 类信号、又查不清的，标"推测"

### 阶段 3：设计防呆装置（只读）

针对体检报告中的每个问题，判断它属于哪一层，**尽量往强的层放**：

1. **最强：改结构，让错误根本写不出来**（例如把不该互通的部分分开放，并禁止互相引用）
2. **强：自动检查**（规范检查规则、类型检查、自动测试，违反就报错、不能提交）
3. **中：运行验证**（让 AI 启动程序实际试用、截图、跑测试）
4. **弱：文字规则**（写进 AGENTS.md / CLAUDE.md 之类的说明文件。只用于必须靠判断的情况）
5. **最弱：人工检查**（靠使用者自己看。尽量避免，因为使用者不懂代码）

输出一张清单：问题 → 建议放在哪一层 → 怎么做（大白话）→ 难度（简单/中等/困难）。标出**最推荐先做的 3 条**：优先选"收益大、风险小、容易做"的。

### 阶段 4：上线就绪评分 + 功能地图草稿（只读）

1. **起草功能地图。** 列出项目的每个功能：叫什么、怎么操作、怎样算正常、属于哪个区域、怎么自动验证。用使用者能看懂的话写。模板见 `templates/docs-功能地图.md`。请使用者逐条确认，不确定的标"待确认"，不要替使用者拍板。
2. **对账。** 从代码里列出所有入口（页面、接口、命令、定时任务、消息处理），和地图逐条对。对不上的列进地图的「对账」表。
3. **按区域给五项前提打分。** 区域按功能地图划分。每个区域、每项前提打一个分：✅ 达标 / 🟡 部分 / ❌ 没有。每个分都要写依据，没有依据就打 ❌，不要按"看起来像有"打分。模板见 `templates/docs-上线就绪.md`。
4. **标风险等级**（规则见阶段 7），每个区域标 🟢 / 🟡 / 🔴。
5. 给出最简单的补齐路线：哪个区域离免审上线最近，先补哪一项。

这一阶段还没做过埋雷测试，所以前提 2、3 最多打 🟡。

使用者同意后，写入 `docs/功能地图.md` 和 `docs/上线就绪.md`。之后每完成一项改动都更新评分。

### 阶段 5：装防呆装置（需逐条批准）

每次只做使用者批准的那一两条：
1. 改之前：确认在新分支上操作（git 仓库则新建分支；不是 git 仓库则先建议使用者备份或初始化 git），并说明会改哪些文件。
2. 实现防呆装置。如果是新增检查规则，先让它对**新代码**生效；旧代码中已有的违规，列成待清理清单，分批处理，避免一次改动过大。
3. 清理该问题对应的旧坏样板（同样需要批准，可以分批）。
4. **关卡演示 + 交证据**（见「关卡演示」）；再运行全部现有测试和检查，证明原有功能没坏。把命令和结果用大白话总结给使用者。
5. 在 `docs/守门规则.md` 里追加一条记录：日期、加了什么检查、它防的是什么错误（大白话）、演示结果。

### 阶段 6：搭上线流水线（需逐条批准）

**先读 `reference/release-pipeline.md`**，里面有要装的文件清单、使用者要点的设置、每一段的演示方法。

按下面顺序，一次只搭一段，每段搭完都做关卡演示：

0. **AI 换成独立账号。** 只有写权限，没有管理员权限。做不到就停在这里，前提 2 最多 🟡。
   不用 GitHub 合并上线、而是本机脚本发版的项目，按 `reference/release-pipeline.md` 的「本机发版的项目」搭，下面第 2、4 步改用那一节的做法。
1. **装文件。** 把 `scripts/` 复制到项目 `.gardener/bin/`，`templates/gardener-config.json` 复制成 `.gardener/config.json` 并填好区域和 `gate_command`。这一步是红色改动。
2. **6a 强制关卡。** 装 `templates/github/gardener-ci.yml` 和 `CODEOWNERS`，教使用者设置主线保护。演示：失败的改动合不进去；改配置的改动要求使用者批准。
3. **6b 自动验证。** 按功能地图写验证，接进 `gate_command`。处理时好时坏的测试。然后跑第一次埋雷：

   ```bash
   python3 -I .gardener/bin/run_mines.py run
   ```

4. **6c 小步上线与退回。** 项目提供 `deploy.sh`、`rollback.sh`、`.gardener/health.json`，装 `gardener-release.yml` 和 `gardener-ledger.yml`，教使用者建两个部署环境。演示：带问题的版本被自动退回，账本多一条记录，区域变成暂停。
5. 有数据库的项目，按 `reference/release-pipeline.md` 的「数据库和数据迁移」演练一次从备份恢复。

每段完成后更新 `docs/上线就绪.md` 和 `.gardener/config.json` 里的评分，并在 `docs/守门规则.md` 记一笔。

### 阶段 7：按风险分级放权（使用者确认后生效）

**一次改动能不能免审自动上线，由 `release_gate.py check` 判断，不由 AI 判断。** 它要求：区域五项前提都有证据，埋雷全部拦下，没有暂停，变更失败率上界、恢复时间、错误预算都在线内。细节和阈值见 `reference/measurement.md`。

改动的风险等级：

| 等级 | 包括 | 怎么上线 |
|---|---|---|
| 🟢 低风险 | 文档、样式、文案文件，以及只新增测试的改动 | 区域通过 `release_gate.py` 就自动上线；使用者事后看证据摘要 |
| 🟡 中风险 | 一般功能逻辑 | 使用者明确允许这个区域中风险自动上线后，才可以；尽量放在功能开关后面，先对一小部分用户打开 |
| 🔴 永远停下 | 碰钱；权限和登录；删除或迁移数据；密钥；对外发送；**修改关卡本身**（检查规则、CI、主线保护、风险配置、功能地图、账本、雷库、上线和退回脚本）；删除或修改已有测试 | 无论关卡是否全过，都停下等使用者批准最新版本。AI 给出证据摘要：改了什么功能、为什么、验证结果，不要求使用者读代码 |

规则：
- **风险等级由 `risk_scan.py` 判断**：既看路径，也看改动内容里有没有碰钱、权限、删数据、密钥、对外发送的迹象。阶段 1 记下的项目自有函数名写进配置的 `red_keywords_extra`。关键词会误报，这是故意的：误报让使用者多批一次，漏报会让危险改动自动上线。
- **不属于任何已登记区域的代码改动，不能自动上线。**
- **信任靠记录挣来。** 新区域一开始，每次上线都由使用者看证据摘要批准，同时流水线记账。按默认阈值，大约连续 22 次没出事，`release_gate.py` 才放行自动上线。不要为了早点放权去改阈值。
- **AI 不能放松自己的关卡。** 修改检查、CI、保护设置、风险配置、阈值、功能地图，一律是 🔴。
- 放权从一个区域开始。先选一个 🟢 区域，再看实测数字决定要不要扩大，扩大由使用者决定。

### 阶段 8：长期园丁模式（持续）

之后在这个代码库里做任何任务时：
- 每当 AI（包括你自己）犯了错并被纠正，主动问使用者："这个错误以后还可能再犯。要不要把它做成一条自动检查？"
- 同一个问题第二次出现，就**必须**提议把它变成自动检查，而不是只在说明文件里加一句话。
- 发现新的坏样板时，提醒使用者，并提议清理。
- 某次改动被退回，或上线后才发现问题：按「事后追账」记账、补关卡，并用 `run_mines.py harvest` 把这个 bug 做成新雷。
- 每月按 `reference/measurement.md` 的「每月复盘」做一次复盘。
- 每次任务结束，都附上证据：跑了哪些检查和测试，结果如何，`risk_scan.py` 判的等级，`release_gate.py` 的结论，是否自动上线。

## 关卡演示

每加一道关卡、每搭一段流水线，都必须做一次，结果写进 `docs/守门规则.md`：
1. 说明这道关卡要拦什么（大白话）。
2. 在副本上故意制造一个它该拦的错误。
3. 运行关卡，给使用者看它被拦下的结果。
4. 撤掉这个错误，再运行一次，给使用者看它恢复通过。

没有演示过的关卡，在评分里不能算 ✅。

## 衡量检查准不准

检查会错在两个方向：**误报**（说有问题，其实没有）和**漏报**（真问题没发现）。误报靠「检查标准」里的依据和运行证据挡住。漏报使用者看不见，只能量出来。**详细做法先读 `reference/measurement.md`。** 核心规则：

**埋雷测试**
- 用 `run_mines.py` 把已知错误逐个放进临时副本，看关卡拦下几个。
- 一个区域的核心雷至少来自两种来源：历史 bug 反推、使用者描述、变异工具、没参与写检查的 AI 会话。只靠写检查的同一个 AI 设计雷，会有同样的盲区。
- 核心雷必须全部拦下。失效的雷不算拦下。
- **不许为了好看删掉或改简单没拦下的雷。** 雷库是受保护路径。使用者坚持要删时，只能「退役」：在 `docs/埋雷记录.md` 写明原因，并告诉使用者，这个功能从此没有雷覆盖，所在区域前提 3 不算达标，直到补上新雷并拦下。
- 埋雷只能证明想到的错误被拦下。没想到的，靠事后追账。

**事后追账**
- 自动退回由流水线记账；上线后才发现的问题，用 `gardener-ledger` 工作流登记，并在 `docs/漏网记录.md` 写一行大白话。
- 出事的区域自动暂停自动上线。补好关卡、重跑埋雷后，只有使用者本人能恢复。
- 同一类问题漏网两次，回到阶段 3 重新设计这一类的防呆装置。
- 记账是为了补关卡，不是为了追究谁的错。

## 不要做的事

- 不要一次性大规模重构或重写。
- 不要在使用者没同意时删除文件、改配置、改平台设置或安装新工具。
- 不要用"看起来没问题"代替实际运行检查。
- 不要把一大段代码贴给使用者看，除非对方要求。
- 不要只在说明文件里写"以后注意"，就当作问题已经解决。
- 不要在 `release_gate.py` 没放行时自动上线，也不要为了让它放行去改阈值、改账本或改配置。
- 不要放松、跳过或绕开任何关卡，包括为了让自己的改动通过。
- 不要用使用者本人的账号或凭据提交代码、开 PR。
- 不要把时好时坏的测试重跑到通过就算数。
- 不要替使用者确认功能地图、风险分级、SLO 或放权范围。
- 不要删掉、改简单没拦下的雷，也不要漏记任何一次漏网。
